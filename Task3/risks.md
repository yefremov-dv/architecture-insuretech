### Ниже приведен анализ влияния планируемого роста нагрузки для каждого интеграционного сценария задания №3
`По условию рост нагрузки удвоится: из 5 подключенных компаний станет 10`

Перечень рисков и проблем текущей архитектурной реализации
1. Сервис **ins-product-aggregator** будет запрашивать в два раза больше организаций, что кратно увеличит вероятность задержки ответов и ошибок при взаимодействии с API страховых компаний
2. Текущее взаимодействие является синхронным и системы будут вынуждены ждать ответа от всех страховых компаний. Если какая-то из новых подключенных компаний допустит ИТ-инцидент, то сервисы **core-app** и **ins-comp-settlement** не получат ответа от всех десяти компаний, включая изначальные пять.
3. Т.к. сервисы **core-app** и **ins-comp-settlement** локально хранят реплики данных о продуктах и тарифах, то при двухкратном росте числа партнеров кратно увеличится занимаемое дисковое пространство.
4. Сервис **ins-comp-settlement** раз в день отправляет запрос в **core-app**, который выгружает полный перечень всех новых страховок за день. Такой единый большой запрос может значительно замедлить работу сервиса **core-app**
5. Согласно схеме, сервисы **client-info** и **ins-comp-settlement** используют один и тот же инстанс БД **ins-comp-settlement-db**, создавая потенциальную точку отказа при кратном увеличении нагрузки. Создается ситуация, когда рост числа запросов от B2C клиентов может создать недоступность сервиса взаимодействия с B2B партнерами через API и наоборот.
